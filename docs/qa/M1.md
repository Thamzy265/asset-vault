### Observations and spec gaps (for the lead)

- **S1 (spec gap): which tables must carry owner and visibility.** The plan AC says "every table has `owner`, `visibility` and timestamps". The design note gives those columns to business records (only `people` today); `users` has timestamps only, `_meta` only `updated_at`, `audit_log` has `at`. I read "business table" as in the lead's brief and the design note, so criterion 1 is PASS. If the PM meant literally every table, `users` and `_meta` fail. Decision for the lead: confirm the reading (and reword the plan AC).
- **S2 (spec gap): "owns nothing".** The brief and README ("It owns nothing") say `vault_app` owns nothing. In fact pg-boss creates its job tables as `vault_app` in the `pgboss` schema, so it owns 67 objects there (design 0004 comment and README also say the app uses the `pgboss` schema). No business table, `audit_log` or `public` is owned, and the audit protections hold (criterion 4), so I marked PASS. Decision for the lead: keep and reword README, or give `pgboss` to another owner.
- **O1 (observation, minor): applied version is `null` during a rollback.** The developer's steps expect "applied one step behind"; after the 0004 down the app role has lost its grants (that is what 0004 grants), so health can't read `kysely_migration` and shows `"applied":null` and `workerHeartbeat: null`. It is still 503, which is the criterion. A rollback of 0003 or older cannot be shown on a populated database (refused by design).
- **O2 (observation): Postgres's own log keeps the failing row.** My deliberate bad inserts made Postgres log `DETAIL: Failing row contains (...)` with the synthetic name and the statement (14 lines, all from my manual psql). The repository validates first (review L1), and the repository run produced 0 names in web, worker and migrate logs, so the app path is clean. Anyone who runs manual bad inserts in production writes names into the Postgres log: worth a README line, lead's call.
- **O3 (observation): `vault_app` can DELETE `users` rows** (the design lists users among the business tables; the audit FK `ON DELETE RESTRICT` blocks deleting a user who has audit rows). Not a criterion; recorded because decision 8 says users are deactivated, not deleted.
