Family Asset Vault — MVP plan

One private place at home for every family asset, policy and document, with a USD net-worth total.

Use the arrow keys to move between slides · Print to save as PDF · Detail: docs/design/00-design-doc-review.md and docs/PLAN.md

Problem and users

The family's wealth and paperwork are scattered across three currencies and many places

Who

Two family members at launch (admin + member), more later. On phones and computers.

The job they are doing

Know what the family owns, what it is worth in USD, where each policy and deed is, and what needs attention.

Today's pain

Plots, houses, shares and policies in MWK, GBP and USD; documents in different places; in an emergency nobody can find the policy number.

Success measure

Every asset and policy entered; a USD total updated nightly; any family member finds a policy's claim contact in under 1 minute.

Source: Family Asset Vault – Design Doc.md, §1–2.

Scope for this phase (MVP)

Records and totals first; the AI features wait for proof they work on this box

In this phase

  • M1 Foundation: sign-in with 2FA, remote access, backups with restore test, audit log
  • M2 Core records: people, assets, properties, insurance, documents, printable emergency summary
  • M3 Dashboard: valuations, FX rates, nightly USD net worth and chart
  • M4 Trading 212 sync · M5 Reminder emails
  • M6 Model speed test, then document reading with a review form

Deferred (Later lines with triggers)

  • Chatbot, trigger: model answers ≥ 8/10 test questions right in < 30 s
  • Forecasting, trigger: ≥ 24 months of history
  • AI-written monthly report, trigger: model test passes + 3 months of reminders
  • Automated property comparables, trigger: your yes (D7) + ≥ 30 manual comparables per area
  • Per-record permissions UI, trigger: a third account, or you ask to hide a record

Options

How to build the core so it fits in 16 GB next to the AI model

Option A: plain Postgres + auth library

  • One TypeScript app + one worker + Postgres; files on an encrypted disk
  • About 1.5–2 GB RAM, leaving room for a bigger model
  • We write the visibility checks ourselves (one tested layer)
  • Effort: lower to run and upgrade

Option B: self-hosted Supabase (as in the doc)

  • Built-in auth, row-level security and storage
  • About 10 containers; several GB, does not fit the 3–4 GB slot
  • Smaller AI model, or less RAM for everything else
  • Effort: more moving parts to upgrade and back up

Recommendation

Option A, because it fits the hardware and is simpler to keep running. This reopens a choice the doc marks as decided, so it is yours (D3).

Security

A home server holding deeds and policy numbers must be hard to reach and easy to restore

Trust boundaries

  • Internet → Cloudflare → app
  • Uploaded PDFs and photos
  • Trading 212 and FX API responses
  • Email provider (outbound)

Abuse cases

  • Someone takes over a family email and passes the Cloudflare gate
  • A crafted PDF attacks the parser
  • Disk or backup stolen
  • Server dies with no restorable backup

Mitigations

  • Mandatory 2FA in the app as the real gate
  • Parsing in a worker with no network
  • Encrypted disk and backups; key kept off the server
  • Monthly automated restore test

Admin tools over Tailscale only; no open router ports; audit log of who viewed or changed records. Review findings C1, C2, F3–F5, H3.
